# 安全审查指南

只在变更涉及安全边界或存在具体安全候选问题时加载本文件。清单用于追踪数据流，不用于按关键词制造漏洞。

## 先建立威胁路径

每个安全 finding 都应能回答：

1. **攻击者能力**：谁能控制输入，需要什么权限？
2. **入口**：HTTP/RPC 参数、文件、消息、环境、依赖或持久化数据从哪里进入？
3. **危险操作**：命令执行、查询、模板、文件系统、反序列化、授权决策或密钥操作在哪里发生？
4. **现有保护**：验证、编码、参数化、sandbox、权限检查是否覆盖了这条路径？
5. **结果**：攻击者能读取、修改或执行什么？影响哪个租户或系统？

只看到危险 API 但不能建立可达路径时，标为待验证风险。Critical 必须有清晰攻击路径和高影响，不能仅靠模式匹配。

## 通用检查

### 输入与注入

- 在危险操作要求的语义层验证输入；白名单只在值域有限时更合适。
- SQL/NoSQL/LDAP 查询使用对应驱动的参数化机制。
- shell 命令优先使用参数数组并避免 shell 解释；清理字符串通常不足以证明安全。
- URL 抓取验证协议、解析后的主机/IP、重定向和内网地址，防止 SSRF。
- 文件访问在规范化后验证仍位于允许根目录。`path.join` 本身不能阻止 `../`。
- HTML、模板和日志在正确的输出上下文编码；不要混用 HTML、JS、URL 编码。

### 认证与授权

- 授权发生在每个受保护对象和操作之前，并验证租户/资源归属。
- 不把前端隐藏、可伪造 header、未签名 token claim 或环境变量当作授权。
- token/session 有适当的签发者、受众、过期和撤销策略。
- 默认分支、错误和缓存不会绕过策略。

### 敏感数据与加密

- 密钥、token、密码和个人数据不进入源码、日志、错误或遥测。
- 密码使用专用 password hashing；普通 SHA/MD5 不是密码哈希。
- 加密模式、nonce/IV、随机数和证书验证符合所用库的安全 API。
- 比较密钥或签名时考虑恒定时间比较；不要自行设计密码协议。

### 依赖与供应链

- 新依赖的来源、维护状态、已知漏洞和 license 与项目约束匹配。
- lockfile 变更应与声明依赖一致；版本固定是可复现策略，不单独证明供应链安全。
- CI 脚本、安装钩子、下载执行和发布权限按最小权限处理。

## 语言相关热点

### Go

- `os/exec` 参数是否可能经过 shell；`Command` 参数数组和 `sh -c` 的风险不同。
- goroutine 访问共享状态是否遵循一致同步；panic 是否越过真正的进程边界。没有 `recover` 不自动构成漏洞。
- HTTP response body、timer、ticker、goroutine 和 context 是否在失败/取消路径释放。
- 路径检查使用规范化后的绝对/相对关系，而不是只查 `..` 子串。

### Python

- 不可信数据不能进入 `eval`、`exec`、unsafe YAML loader 或 pickle。
- subprocess 使用参数数组且避免 `shell=True`；模板、SQL 和路径使用各自的安全 API。
- archive 解压验证目标路径，防止 Zip Slip。

### JavaScript / TypeScript

- DOM 注入根据 HTML/attribute/URL/JS 上下文处理；`textContent` 只解决文本节点场景。
- `child_process.exec`、动态代码执行、原型污染和不安全 redirect/URL 是重点数据流。
- `JSON.parse` 的异常处理属于可靠性问题，除非能进一步证明安全影响。

### Java / Kotlin

- 不可信反序列化、表达式语言和反射调用需要类型/类白名单或替代格式。
- XML parser 显式禁用外部实体和外部 DTD。
- Log4Shell 风险取决于实际 Log4j 版本和配置，不能仅因日志包含外部字符串就下结论。

### Rust

- 审查 `unsafe` 的安全不变量、FFI 指针/长度/生命周期和整数转换。
- 路径、命令和反序列化仍需按不可信输入处理；内存安全不等于业务安全。

## 定级校准

- **Critical**：未经授权的跨租户访问、RCE、可利用的密钥泄露、大规模不可恢复数据损坏。
- **Major**：可利用但范围受限的越权/注入、持久敏感数据泄露、现实可触达的 DoS。
- **Minor**：纵深防御缺口或低影响暴露，且不存在已证明的高影响路径。

不确定漏洞是否可利用时降低置信度，不要用提高严重性来表达不确定性。
