# Issue 分析指南

Issue 分析的目标是判断问题是否成立、是否值得处理、定位最可能的责任边界，并给出可验证的下一步；不要默认每个 Issue 都需要代码修复，也不要在未读代码时虚构根因或精确工作量。

## 分析顺序

1. 提炼期望行为、实际行为、复现条件和版本/环境。
2. 区分 bug、功能需求、行为澄清、支持请求或重复问题。
3. 阅读评论、关联 PR/Issue、日志和复现材料，区分事实与猜测。
4. 在仓库可访问时定位入口、调用链、状态边界和现有测试。存在 `.codegraph/` 时优先使用 CodeGraph。
5. 评估期望行为是否符合项目定位、产品语义和已有契约，问题是否属于项目责任边界，是否已解决或有重复项。
6. 比较用户或业务收益与兼容性、复杂度、迁移和长期维护成本，并检查配置、文档、运维或上游修复等更小替代方案。
7. 提出最小验证步骤；有证据后再给根因和修复方案。

## 合理性判断

使用代码、文档、历史行为、复现材料、关联讨论和明确业务场景作为证据，分别判断“诉求是否成立”和“是否值得由本项目现在处理”。固定分类为：

- **合理**：问题或需求成立，且符合项目目标和责任边界，处理收益与成本匹配。
- **部分合理**：核心诉求成立，但期望、范围、优先级或处理方式需要调整。
- **不合理**：证据表明诉求与已有契约、项目目标或责任边界冲突，或处理成本明显超过收益。
- **证据不足**：缺少复现、版本、调用方、业务目标等决定性信息；列明需补充的证据。

低频或低优先级不自动等于不合理。缺少未公开的业务背景也不能作为拒绝依据。Issue 可以建议非代码处理；若重复、已解决、由上游负责或现有行为符合明确契约，可建议关闭或无需处理。

## 输出

```markdown
## 判断
- 类型：
- 优先级：
- 合理性结论：合理 / 部分合理 / 不合理 / 证据不足
- 建议动作：接受处理 / 缩小或改写 / 补充证据 / 延期 / 拒绝或关闭 / 无需处理
- 核心问题：

## 已知证据
- ...

## 分析
- 合理性依据：
- 业务或用户收益与成本：
- 可替代方案：
- 最可能的责任边界：
- 仍缺少的信息：

## 建议
1. 首选验证或修复方向
2. 必要时的替代方向
```

只有证据足够时才写“根因”；否则使用“假设”，并给出能够证伪它的测试。工作量只给相对量级及其前提，不伪造精确天数。若 Issue 已解决或被替代，优先说明当前状态和后续是否仍有行动项。
