# Issue 分析指南

Issue 分析的目标是判断问题是否成立、定位最可能的责任边界，并给出可验证的下一步；不要在未读代码时虚构根因或精确工作量。

## 分析顺序

1. 提炼期望行为、实际行为、复现条件和版本/环境。
2. 区分 bug、功能需求、行为澄清、支持请求或重复问题。
3. 阅读评论、关联 PR/Issue、日志和复现材料，区分事实与猜测。
4. 在仓库可访问时定位入口、调用链、状态边界和现有测试。存在 `.codegraph/` 时优先使用 CodeGraph。
5. 提出最小验证步骤；有证据后再给根因和修复方案。

## 输出

```markdown
## 判断
- 类型：
- 优先级：
- 核心问题：

## 已知证据
- ...

## 分析
- 最可能的责任边界：
- 仍缺少的信息：

## 建议
1. 首选验证或修复方向
2. 必要时的替代方向
```

只有证据足够时才写“根因”；否则使用“假设”，并给出能够证伪它的测试。工作量只给相对量级及其前提，不伪造精确天数。若 Issue 已解决或被替代，优先说明当前状态和后续是否仍有行动项。
